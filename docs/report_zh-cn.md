# 浏览器内 JVM 的执行栈性能实测报告

> **日期**：2026-10-31
> **平台**：Apple M4 Max MacBook Pro（Apple Silicon，arm64）
> **测试浏览器内核**：Firefox 158.0.1（Gecko，JS/WASM 内核 SpiderMonkey）、Chrome 155.0.8059.86（Chromium，JS/WASM 内核 V8）、Safari 26.6.2 (21624.5.1.11.3)（WebKit，JS/WASM 内核 JavaScriptCore）
> **基准**：本地 HotSpot Temurin 21.0.11；浏览器内 CheerpJ 4.3 与 b-jvm（anematode/b-jvm，克隆于 2026-10-30，JDK 23 运行时）

---

## 1. 背景与问题链

本实验源于一个问题：应用在 iOS 上使用 JIT 会怎样。结论是内核会以代码签名违规为由直接 SIGKILL——除非进程持有 `dynamic-codesigning` entitlement，而该 entitlement 实际只授予了浏览器内核的 JS/WASM 引擎（如 Safari 中的 JavaScriptCore）。

由此推出本报告的核心问题：**当"能 JIT 的只有浏览器内核"时，网页里运行的 JVM，其 JIT 编译器只能以"字节码 → JS/WASM"的形态存在，最终机器码由宿主内核生成。这条链路的真实性能是什么水平？**

执行栈共四种：

| 执行栈 | 位置 | 说明 |
|---|---|---|
| HotSpot `-Xint` | 本地 | 纯解释器基线 |
| HotSpot JIT（C1/C2） | 本地 | 原生 JIT 基线 |
| CheerpJ | 浏览器 | JVM 的 JIT 生成 JS，由宿主内核再编译；解释器为 WASM 实现 |
| b-jvm | 浏览器 | 纯 WASM 解释器（其 JIT `dumb_jit` 在当前源码中被作者无条件禁用，实测 jit/interp 两形态数值一致证实了这一点） |

## 2. 实验设计

单一 `Bench.java`，7 个负载 × 2 种调用形态：

**负载维度**：

| 代号 | 内容 | 考察点 |
|---|---|---|
| MATH | `Math.sin` 累加 | native 桥接开销，预期 JIT 提升最小 |
| INT | int 求和循环 | 基础代码质量；HotSpot 会做归纳变量消除 |
| LONG | long 求和循环 | 64 位整数在 JS 目标上的表示成本 |
| ARRAY | 数组访问 + 可预测分支 | 边界检查消除能力 |
| INVOKE | 微小方法高频调用 | 内联能力 |
| ALLOC | 每轮分配小对象 | 逃逸分析/标量替换能力 |
| VIRTUAL | 单态接口调用 | 去虚化 + 内联能力 |

**形态控制**（唯一组间变量）：

- interp 形态：单方法 3 次大调用（数百万次迭代），调用计数低于分层编译阈值；
- jit 形态：800 次预热 + 5 轮 × 400 次小调用，跨越调用计数阈值触发 JIT。

**自校验机制**：每负载校验和跨形态、跨运行时必须一致（全部数据点 chk=OK）；逐轮输出使 tier-up 与去优化直接可见。

**一次重要的方法学教训**：形态控制对 HotSpot 有效，但对 CheerpJ 不安全——其分层计数比预期激进且编译触发异步，导致部分"interp 形态"数据实际已被编译（见第 3 节污染标注）。b-jvm 无 JIT，两形态天然等价，成为最干净的解释器参考组。

## 4. 逐维度分析

### 4.1 紧凑整型循环：三内核全部达到 HotSpot C2 水平

INT 在 CheerpJ JIT 下于三个内核均为 0.22–0.23 ns/iter，与 HotSpot JIT（0.24）**完全持平**。每迭代约一个时钟周期，说明 CheerpJ 生成的 JS 被 V8、SpiderMonkey、JSC 三家内核都优化到了极致紧凑的循环。**"编译到 JS"这条路线的天花板没有被内核卡住——至少对最简单的数值代码如此。**

### 4.2 64 位税：从"路线固有成本"修正为"内核组合病态"

LONG 的三内核数据（Gecko/SpiderMonkey 1.44 / Chromium/V8 17.7 / WebKit/JavaScriptCore 18.7）推翻了本轮实验前"long 税是 V8 特有"的中间结论：**JSC 同样有税，只有 SpiderMonkey 无税**。b-jvm 对照组（WASM 原生 i64）在三内核上 LONG/INT 比值均 ≤ 1.2，证明 WASM 路线无此税。结论：long 税是"CheapJ 生成物中 long 的 JS 表示 × 具体内核优化路径"的组合属性；选用"编译到 JS"路线时它是一个**内核风险**而非确定成本。

### 4.3 调用密集负载：V8 与 JSC 内核的共同病态点

INVOKE/VIRTUAL 呈现清晰的两极：SpiderMonkey 1.6 ns，V8 与 JSC 均为 11.1–11.7 ns（差 7 倍）。且 JSC 上该值与 CheerpJ 自身解释态（12.0）几乎相同——**在 Safari 上，CheerpJ 的 JIT 对调用密集代码的净收益约等于零**（INVOKE：解释态 12.0 → 编译态 11.7）。V8 与 JSC 对这类"每方法体积极小、调用频度极高"的生成 JS 无法有效内联，是跨内核分化最大的维度。

### 4.4 分配与数组：JSC 的双峰行为

ALLOC 与 ARRAY 在 Gecko/Chromium 上为 1.1–1.6 ns，WebKit 上却落在 18.8–19.5 ns。JSC 呈现明显的**双峰**：要么优化到极致（INT 0.22），要么停在一个 ~19 ns 的平台（LONG/ARRAY/ALLOC 几乎同值）。一个合理的推断（未确认）：JSC 对 CheerpJ 生成物中的这些模式只应用了基线层优化而未进入最优层，或其属性/数组的内联缓存对生成代码的形状不友好。19 ns 平台与三种不同负载同值这一事实本身支持"卡在同一非优化层"的解释。

### 4.5 MATH：唯一跨栈"损耗可见"的维度

CheerpJ JIT 各内核 16.6–26.2 ns，对照 HotSpot 1.96 ns——差距不在 `sin` 本身，而在每次调用跨越的 native 桥接。它与 JIT 质量无关（这正是设计该维度作为"JIT 提升最小"对照的目的），并给出一个通用信号：**当负载瓶颈在宿主运行时服务而非字节码执行时，"JVM JIT"这条链路的提升空间被结构性地封顶**。

### 4.6 ALLOC 与 GC：两个内核各自的快照

- b-jvm（FF）ALLOC round0 = 3336 ns，随后稳定 584 ns：其单线程压缩 GC 的首次回收被完整拍到，暂停约为稳态的 5.7 倍；
- b-jvm 的分配稳态（Safari 59.8 ns）仍比 HotSpot `-Xint`（29.3 ns）慢 2 倍，但比其自身其他负载的放大倍数小——bump allocation + 紧凑 GC 是 b-jvm 相对最强的维度。

## 5. 跨内核横向发现

### 5.1 解释器的内核敏感度 >> 生成代码的内核敏感度

b-jvm（WASM 尾调用解释器）跨内核差距 **3.4–4.8 倍**；CheerpJ JIT 生成物（除病态维度外）跨内核差距通常 < 2 倍。**解释器对宿主内核 WASM 引擎质量的依赖，远大于 JIT 生成物对宿主内核 JS 引擎质量的依赖**——后者因为生成物足够简单规整，各家都能优化好；前者的性能直接由尾调用实现质量决定。

### 5.2 内核排名因工作负载类型而完全颠倒

- WASM 解释器（b-jvm）：**WebKit < Chromium < Gecko**（WebKit 最快，6.2 vs 27.2 vs 87.8 ns，Gecko 慢 14 倍）。WebKit 的 WASM 尾调用实现虽最年轻（2024-08 才修复栈参数形态的尾调用），却是三者中最快的——这是本轮最意外的结果，也推翻了实测前"WebKit 新实现大概率偏慢"的预测。
- CheerpJ 生成 JS：**SpiderMonkey 综合最优**（七个负载无一病态）；V8 与 JSC 各有病态维度（long、调用密集；JSC 另加 alloc/array）。

没有任何一个内核在两类工作负载上同时领先。**"哪个浏览器内核跑 Java 快"没有单一答案，取决于执行栈是解释器还是 JIT 生成物。**

### 5.3 去优化的真实风险（Chrome，上一轮实测）

Chrome 上 CheerpJ INT 曾出现第 0–2 轮 0.23 ns、第 3–4 轮跳回 4.24 ns 且不再回升的完整去优化生命周期。生成物不是终态，宿主随时可以收回优化——这是该架构的固有风险，测量时必须逐轮输出才能捕获。

## 6. 回到最初的问题：iOS 上的 JVM

macOS Safari 与 iOS 的浏览器内核同为 WebKit（JS/WASM 内核均为 JavaScriptCore），因此 Safari/WebKit 基本可视为 iOS 列（内存等资源差异除外）：

1. **iOS 网页里跑 JVM 是完全可行的**，且在最好的维度上（紧凑 int 循环）达到与桌面 HotSpot C2 相同的每迭代周期数。
2. CheerpJ（JIT 路线）在 JSC 上的短板是 long、数组、分配、方法调用（~19 ns 平台与 ~11.7 ns 调用开销），整体水平约等于"HotSpot 解释器的 1–2 倍速"，远好于任何 WASM 解释器在同一内核上的表现（6.2–59.8 ns）。
3. b-jvm（解释路线）在 JSC 上反而是三内核中最快的，INT 6.19 ns 仅比本地 HotSpot 解释器慢 1.6 倍——如果应用特征无法被 CheerpJ 的 JIT 有效覆盖（例如调用密集型），iOS 上的最优解可能恰恰是解释器。
4. 对 iOS App（非网页）而言，结论维持第一轮的分析：自行生成机器码会被内核 SIGKILL；把代码生成权上交给 JSC（通过 WKWebView/JS API）是唯一合法且经本实验验证性能可接受的路径。

## 7. 局限与未确认事项

- CheerpJ 的 ALLOC 编译态是否做了标量替换无法区分（1.1–1.4 ns 与无分配循环地板同值）；JSC 19 ns 平台的成因（基线层假设）为推断。
- 单轮异常已剔除说明：Chrome b-jvm INT round2 = 52.3 ns 为孤立异常（前后轮 19–26），不影响均值结论；FF b-jvm ALLOC round0 为 GC 快照。
- 所有数字限于合成微基准，不可直接外推到真实应用负载；方法调用密集的真实 Java 程序在 V8/JSC 上会显著偏向本报告的病态维度。
